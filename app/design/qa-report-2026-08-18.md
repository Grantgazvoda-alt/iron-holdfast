## 3. Findings

### F-001 — Floating stone terrain sprites in the top-left quadrant — **High (visual — launch quality)**

**Description**
In the live build, the top-left area of the map (above the western forest strip, near the grass/forest/water boundary) renders grey, stone-like "L-shaped" patches that float over the tree and grass tiles. They are disconnected from the terrain logic — i.e. they appear to be artifact sprite fragments rather than game objects from the map data (no buildings/enemies exist there). They do not affect gameplay but visibly degrade the "realistic, polished" presentation target.

**Deviation:** They remain visible and static; expected terrain texture continuity; artifacts break the painterly seam between forest and grass.

**Perceived risk:** Cosmetic; impact limited to visual polish at launch. Marked High because the current request thread is specifically the visual-art upgrade — the live public build violates that goal until this ships.

**Reproduction:**
1. Open https://iron-empire.higgsfield.app
2. Click "Begin the hold"
3. Skip the tutorial (or let it run)
4. Pan/zoom to the map top-left corner (north-west, above the forest strip west of the keep)
5. Observe the grey "stone quarry-like" texture shapes floating over trees/grass, disconnected from any adjacent quarry/stones.

**Expected:** Terrain texture everywhere is the natural painted base (grass blades, forest canopy, rock outcrops from the painter).
**Actual:** Stone-shaped grey patches overlay tree/grass tiles in the top-left.

**Status / verification:** Confirmed via vision analysis of a live screenshot during the playtest. The pending `a5fa1e1` art pass rewrote the entire terrain painter (`paintTerrain` with value-noise dappling, explicit rock outcrop/vein layer, forest canopy) — the legacy painter path that produced these artifacts is replaced in that commit, so this is **likely already fixed in the pending build**, but the pending build is **not yet live** (see §6). **Retest on the new build is mandatory before closing.**

### F-002 — (RESOLVED) Frozen game clock observed in the browser — no server defect **Info)

**Description:** During automated play, the on-screen timer stayed fixed at "8:39" and the wave countdown static on multiple data points...; resource counters (wood 35) remained constant for minutes, and the pause button label never flipped.

**Diagnosis:** Server-loaded probes on the same endpoints show the sim ticking normally: `nextWaveIn` decrement per tick, `time` advancing every 0.5s, `paused:false`. A subsequent *raw* WebSocket session on a fresh room reproduced normal ticking even before any building action. The in-browser observation is therefore attributed to the test-harness/browser session anomaly documented in F-003 — **not** a game defect.

**Status:** RESOLVED — no product bug; environmental artifact of the test tooling. If a real player reports a frozen clock, treat the report as live-server or the client → verify the client's socket reconnect loop (already guarded in code) rather than the sim engine.

---

### F-003 — Test harness anomaly: browser session drifting to unrelated third-party sites — (Tooling)

**Description:** The automated browser used for playtesting repeatedly navigated away from the game to a landing-page domain, `settup.e-pos.id` (a foreign construction template), mid-test. Canvas lookups then fail until re-nav to `iron-empire.higgsfield.app` restored the game page. This broke long-running in-browser timing measurements and twice produced misleading "frozen run" observations (see F-002).

**Product impact:** None — it is an artifact of the shared/managed browser environment used for testing, not of game client/server code.

**Mitigation:** For future automated sessions: (1) re-assert the game host before each measurement, (2) prefer protocol probes (raw WS) for timing/state assertions, (3) use the browser only for DOM/render/UI checks.

**Reproduction:** Run long automated browser sessions against the public game URL in a shared browser runtime.

### 4.3 Tool selection & build flow — PASS
- `.tool[data-b]` elements toggle an `active` class on click (verified `house` → active).
- With a tool active, canvas click in build mode sends `{type:"action", action:{type:"build", b, x, y}})` and the wire-level confirmation showed building count 0 → 1.

### 4.4 Server simulation (protocol-level) — PASS
- Live room join; `state` broadcasts at the 0.5s tick (time advances 0→5 in probe window).
- Economy values round-trip `res {wood, stone, gold, iron, food}`.
- Build action accepted; building appears in view.
- Pause: `paused` flips to `true` and ticking stops; pause-off resumes ticking (`t 2 → 3 → 4` observed).
- Wave scheduling counter `nextWaveIn` decrements per tick.

### 4.5 First-run gate — PASS
- Tutorial shown on the first session after a reset (fresh localStorage), not re-shown on subsequent room starts in the same origin — gated by `ironhold:tutorial` flag in localStorage.

### 4.6 Audio — PASS (basic)
- Mute button wired to a `musicGain` ramp and persists choice in `localStorage` (`ironhold:muted`).

### 4.7 Console / JS errors — PASS (none)
- `browser_console`: 0 console messages, 0 JS errors across load, tutorial, and gameplay in the stable session.
